# CLAUDE.md

## Overview

This repository analyses match-up data from the HYPERNETS in-water radiometry station(s) in France, comparing HYPERNETS-derived water-leaving reflectance (RHOW / ρw) against satellite ocean-colour sensors. **All four sensor families are wired end-to-end and have populated `output/`/`figures/`**: Sentinel-3 OLCI (S3A/S3B), MODIS-Aqua (AQUA), VIIRS (SNPP/JPSS1/JPSS2), and PACE-OCI (PACE). See `sensor_grid()` in `code/0_functions.R` for the authoritative sensor_Z → sensor_Y mapping.

**Sites: MAFR** (Gironde Estuary mouth — highly turbid) and **THFR** (a lagoon — clear-water comparison site to MAFR). The code (`sensor_grid()`, `global_scatterplot()`) detects sites via `available_sites()` automatically.

**Derived sites (six total, alongside MAFR/THFR):** all independent re-analyses of the same underlying MAFR/THFR match-ups, sourced directly from the SQLite `.db` files rather than the real `Hypernets_matchups` `.csv` output, via `db_export_matchups_site()`/`db_export_matchups_multi()` in `code/0_functions.R`:
- `THFR_NE` — restricts to the NE quadrant of the inner 3×3 pixel grid.
- `THFR_poly` — restricts to a hand-drawn clean-water polygon.
- `THFR_pixel` — no spatial filter, but the full per-pixel QC gate stack still applies (isolates the effect of QC from the two spatial filters above).
- `MAFR_pixel` — the `THFR_pixel` analogue for MAFR, sourced from `mafr_2024.db`/`mafr_2025.db`.
- `THFR_raw` / `MAFR_raw` (added 2026-09-07) — the same 3×3-box reconstruction as `*_pixel`, but with **no pixel-level QC at all** (`apply_pixel_qc = FALSE`), meant to reproduce `Hypernets_matchups`' own unfiltered aggregation as closely as possible.

All six are first-class sites — registered in `available_sites()`'s candidate list, generated by `code/1_matchups_single.R` before `process_sensor()` runs — and **none replaces MAFR/THFR anywhere in the pipeline yet**. `THFR_raw`/`MAFR_raw` exist specifically so `validate_derived_site()` (see below) can check a `.db`-only reconstruction against the real tool output before any such swap is considered. See `db_export_matchups_site()` in `code/0_functions.R` below.

This is a plain collection of R scripts (no package structure, no `DESCRIPTION`/`renv.lock`, no test suite), **numbered by pipeline run order** (`0_functions.R`, `1_matchups_single.R`, `2_outliers.R`, `3_sensitivity.R`, `4_matchups_global.R`, `5_figures.R`). Run scripts interactively/line-by-line in R, RStudio, or Positron from the repository root — several sections are commented-out exploratory/diagnostic code left in place intentionally (e.g. ad hoc checks at the end of `code/4_matchups_global.R`).

## Manuscript context

This codebase supports a manuscript targeting *Frontiers in Remote Sensing*, in the same Research Topic as its scientific/site precursor, **Doxaran et al. 2024** ("Validation of satellite-derived water-leaving reflectance in contrasted French coastal waters based on HYPERNETS field measurements", doi:10.3389/frsen.2023.1290110), which validated HYPERNETS at Berre lagoon (moderately turbid) and the Gironde Estuary/MAFR (highly turbid) against S2-MSI, L8/9-OLI, S3-OLCI, and Aqua-MODIS with multiple atmospheric-correction algorithms. This project reuses Doxaran et al. 2024's **site-contrast framing** (turbid MAFR vs. clear-water THFR, replacing their Berre lagoon site) but adopts the richer **statistical/technical methodology** (`base_stats()`'s Model II/SMA regression, Pahlevan-style log-space Bias/Error, MRD/MARD) developed in a separate, unpublished "in review" manuscript (Schlegel et al., working title "Hyperspectral field and satellite radiometric matchups in oligotrophic waters") describing a moving-vessel Tara HyperBOOST campaign — that paper is a technical/methods precursor only, not a site precursor (it studies oligotrophic open-ocean water, not French coastal sites). See `manuscript/roadmap.md` for the full literature synthesis and step-by-step plan, and `manuscript/track-changes.md` for a running log of repo changes made while developing this manuscript.

**The pipeline is mid-redesign** (as of 2026-09-07) around reading match-ups directly from the SQLite `.db` files with the repo's own explicit per-pixel QC, rather than relying on `Hypernets_matchups`' own opaque internal aggregation. `MAFR`/`THFR` themselves still come from the real tool's `.csv` output for now — see "Data dependency" and the derived-sites list above. A published flow-chart artifact walks through the full current pipeline shape and the open architectural decisions; ask for it or check recent session history if you need the visual.

## Data dependency

Two kinds of external data feed this pipeline, neither stored in this repo:

- **`.csv`/`.sql` match-up files** for the real `MAFR`/`THFR` sites, generated by the external `Hypernets_matchups` tool and read from a fixed local path pattern:
  ```
  ~/pCloudDrive/Documents/OMTAB/HYPERNETS/FR/<site_name>/RHOW_HYPERNETS_vs_<sat_name>/
  ```
  (built by `file_path_build()` in `code/0_functions.R`).
- **SQLite `.db` files** — `thfr_2025.db`, `mafr_2024.db`, `mafr_2025.db`, at `~/pCloudDrive/Documents/OMTAB/HYPERNETS/FR/` — the same underlying HYPERNETS/satellite data `Hypernets_matchups` itself ingests from, read directly by `db_matchup_long()`/`db_matchup_pixels()` to build the six derived sites above. These are not a separate, independent data source from the `.csv` files; they expose the data at an earlier stage, before the real tool's own (opaque) pixel-box aggregation.

Running the full pipeline requires this external data to be present locally; it cannot be reconstructed from this repo alone.

## Running the code

No build/lint/test commands — this is exploratory analysis code executed with `Rscript` or interactively. Source the six scripts in numbered order from the repository root:

```r
source("code/0_functions.R")        # shared library -- always first
source("code/1_matchups_single.R")  # per-file matchup stats
source("code/2_outliers.R")         # outlier screening -> meta/satellite_outliers.csv
source("code/3_sensitivity.R")      # matchup-protocol sensitivity checks + derived-site validation (optional but recommended)
source("code/4_matchups_global.R")  # per-wavelength global stats -> output/global_stats_*.csv
source("code/5_figures.R")          # final figures -> figures/
```

All scripts assume the working directory is the repository root (paths like `"output/..."`, `"meta/..."`, `"figures/..."` are relative).

## Pipeline order

The scripts are **numbered by run order**, driven by file dependencies (later stages read `.csv` outputs written by earlier stages):

1. **`code/0_functions.R`** — shared library, sourced by everything else. Never run standalone.
2. **`code/1_matchups_single.R`** — first regenerates the six derived sites (`db_export_matchups_ne()`/`db_export_matchups_poly()`/`db_export_matchups_pixel()`/`db_export_matchups_mafr_pixel()`/`db_export_matchups_thfr_raw()`/`db_export_matchups_mafr_raw()`, each looping internally across all four sensor families and writing one `meta/<site>_pixel_removals.csv` audit log per site), then runs `process_sensor(sensor_Z)` in matchup mode for all four sensor families: computes per-file match-up stats → `output/matchup_stats_RHOW_<sensor_Z>.csv` and `output/matchup_noQC_stats_RHOW_<sensor_Z>.csv` (files failing the time/distance QC gate, see `process_sensor()`'s use of `site_diff_time_limit()` below).
3. **`code/2_outliers.R`** — semi-manual outlier screening, active for **all four sensor families** (OLCI, MODIS, VIIRS, OCI), across every site (real and derived alike). Uses a satellite pixel-variance CV gate (`sat_var_check()`): OLCI/MODIS/VIIRS use `cv_limit_choice = 30` (top of the script); OCI uses a hard-coded 50% threshold (in the same per-sensor loop) as a temporary workaround while all THFR PACE files have anomalously high CVs — see Bug 8 in `manuscript/upstream-data-bugs.md`. Combines all four sensors' flagged files into `meta/satellite_outliers.csv`. **Must run before `4_matchups_global.R`**, which reads that file. Note: even the standard `cv_limit_choice = 30` gate can legitimately remove 100% of a site/sensor combination's matchups — see Bug 10 (THFR/JPSS2).
4. **`code/3_sensitivity.R`** — two independent jobs in one script, safe to skip in a quick production run but should be re-run whenever MAFR/THFR data or the derived-site reconstruction change materially: (a) empirically justifies the match-up protocol's time-window and distance-window choices (distance sanity check, time-window sensitivity plot + trend test per site, before/after comparison of `daily_closest_matchup()` day-selection via `global_stats_impl(select_daily = ...)`); (b) `validate_derived_site()` calls for every derived site (`THFR_NE`/`THFR_poly`/`THFR_pixel`/`MAFR_pixel`/`THFR_raw`/`MAFR_raw`), diagnostically comparing each `.db`-reconstructed matchup against the real `Hypernets_matchups` file for the same timestamp — see Bugs 12/13 below. Neither job is read by any other script.
5. **`code/4_matchups_global.R`** — `process_sensor(sensor_Z, "global")` for all four sensor families: aggregates match-ups per wavelength → `output/global_stats_RHOW_<sensor_Z>.csv`, combined into `output/global_stats_all.csv`. Reads `meta/satellite_outliers.csv` (written by step 3) via `global_stats()`.
6. **`code/5_figures.R`** — reads the QC'd `output/` and `meta/` files to build final figures into `figures/`: the per-family global scatterplot stacks (MODIS/VIIRS/OLCI/OCI), Figure 1 (MAFR/THFR station map from `meta/station_in_situ.csv`), Figure 3 (HYPERNETS hyperspectral spectrum vs. satellite band-equivalent RHOW for one representative matchup date), Figure 4 (per-satellite HYPERNETS-vs-satellite scatterplots for that same date), Figure 11 (error/bias matrix heatmap faceted by sensor family), and Fig S1 (PACE OCI Error/Bias barplots across all wavelengths).

All four sensor families (OLCI, MODIS, VIIRS, OCI) are wired end-to-end for the MAFR and THFR sites. No code changes needed for the core pipeline itself, though see the site-specific time-window note below.

## Core architecture (`code/0_functions.R`)

Sensor naming has three tiers used consistently across the codebase:
- `sensor_Z` — sensor family / mission group, e.g. `"OLCI"`, `"OCI"`, `"VIIRS"`, `"MODIS"`.
- `sensor_Y` — specific platform/version within a family, e.g. `"S3A"`, `"S3B"`, `"S3_all"`, `"PACE"`, `"VIIRS_N"`/`"VIIRS_J1"`/`"VIIRS_J2"`, `"AQUA"`.
- `sensor_X` — the reference/in-situ system, generally `"HYPERNETS"` (column-named `"Hyp"` inside loaded data frames).

`sensor_grid()` and `W_nm_out()` map `sensor_Z` → `sensor_Y` list and → the fixed waveband set to compare, respectively. `colour_nm_func()` defines the plotting colour palette per `sensor_Y`, keyed by waveband label — note the code comments flag this palette as needing per-satellite-specific colour bands (see the note in `code/5_figures.R`), so don't assume today's palette choices are final.

Function groups, in read order in `0_functions.R`:
- **Utilities**: `file_path_build()`, `load_matchup_mean/long/var()` (parse the semicolon-delimited match-up CSVs; `load_matchup_mean` averages replicate scans and keeps exactly 2 sensor rows per file — mismatches raise a warning), `proc_HYPERNETS_L1C()` (parses HYPERNETS L1C NetCDF files), `sat_var_check()` (per-file satellite pixel variance), `available_sites(sat_name)` (checks disk for a given satellite's `MAFR`/`MAFR_pixel`/`MAFR_raw`/`THFR`/`THFR_pixel`/`THFR_NE`/`THFR_poly`/`THFR_raw` data folders; used by `sensor_grid()`/`global_scatterplot()` so a site is included automatically once its data folder exists), `site_diff_time_limit(site_name)` (site-specific match-up time-window limit in minutes — **MAFR = 30, THFR = 30** since 2026-09-10, raised from MAFR = 15 after an empirical check found the wider window nearly doubles usable MAFR matchups for a small (~1 percentage point) rise in median `Error_50`; see below), `site_rhow_limit(site_name)` (added 2026-09-03 — site-specific RHOW plausibility ceiling, MAFR = 0.25/THFR = 0.05, derived from the empirical max HYPERNETS RHOW observed per site; applied as a QC gate to both Hyp and satellite values, skippable via `apply_pixel_qc` below), `sensor_resolution_km(sensor_Y)` (added 2026-09-03 — nominal per-sensor nadir pixel resolution in km; not currently used by the whole-matchup distance gate, which is a flat ceiling — see the Time/distance QC gate note below), `site_pixel_min(site_name, sensor_Y)` (added 2026-09-04 — minimum valid-pixel count per matchup-wavelength before `write_matchup_csv_db()` will compute a pixel-box mean, mirroring the real tool's own documented "≥6 of 9" rule; every derived site including `*_raw` has an entry), `daily_closest_matchup(df, site_name)` (added 2026-07-10 as `daily_average_matchups()`, **replaced 2026-09-03** with closest-in-time selection instead of averaging — same-day HYPERNETS scans and satellite overpasses are not independent measurements of the same water, so only the temporally-nearest pairing per calendar day is retained rather than blended).
- **`.db`-sourced matchups**: `db_matchup_long(db_path, sensor_Y, agg_method)` and `db_matchup_pixels(db_path, sensor_Y)` read matchup pairs directly from a `Hypernets_matchups` SQLite database — the former aggregates each side (Hyp and satellite) to one value per matchup×wavelength with no per-pixel QC applied (used for SRF-convolution/diagnostic work, not the main matchup-stats pipeline), the latter keeps the satellite side at raw per-pixel resolution for the caller to gate/aggregate itself. `db_expand_measure_info_ids()` (added 2026-09-07, fixing Bug 12) caps the raw replicate expansion for HYPERNETS scans to the first 3 of 6 bundled rows, matching what the real tool actually uses — this closed nearly the entire Hyp-side reconstruction discrepancy (down to ~0.00001-0.5% median). The satellite pixel-box side has no equivalent fix: `write_matchup_csv_db()`'s plain arithmetic mean of surviving pixels differs from the real tool's own (undocumented, unrecoverable-from-schema) box-averaging formula by a persistent 3-58% median — see Bug 13.
- **Derived-site export**: `db_export_matchups_site(sensor_Z, site_name, pixel_filter_fn, file_tag, qc_site_name, db_path, apply_pixel_qc = TRUE)` is the shared driver behind all six derived sites — reads raw per-pixel matchups directly from the SQLite database (`db_matchup_pixels()`), applies the whole-matchup `diff_time` gate unconditionally, then (only if `apply_pixel_qc`) the per-pixel RHOW-ceiling/negative-value/distance gates (using `site_rhow_limit(qc_site_name)`; `qc_site_name` states which real site's QC policy applies — `"THFR"` for the THFR-derived sites, `"MAFR"` for the MAFR-derived ones, independent of the derived site's own name), then applies a site-specific `pixel_filter_fn` (`pixel_filter_ne_inner3x3`, `pixel_filter_clean_water`, or `pixel_filter_inner3x3`) before writing new per-matchup CSVs via `write_matchup_csv_db()` into a new site folder. Every dropped pixel/gate is captured by `log_gate_drop()` into a `removal_log` tibble, combined across sensor families and written to `meta/<site>_pixel_removals.csv` by the thin per-site wrappers (`db_export_matchups_ne/poly/pixel/mafr_pixel/thfr_raw/mafr_raw()`; `db_export_matchups_multi()` loops a site across more than one `.db` file, needed for MAFR's two yearly files). `apply_pixel_qc = FALSE` (the `*_raw` sites) skips only the four pixel-plausibility gates, not the `diff_time` gate, the spatial filter, or `write_matchup_csv_db()`'s own `site_pixel_min()` gate. Adding a further derived site needs only a new `pixel_filter_*()` function (if the inclusion rule is new) plus one more wrapper.
- **Validation diagnostic**: `validate_derived_site(site_name, tag, real_site_name)` (called from `code/3_sensitivity.R`, not a standalone script despite older comments elsewhere referencing a `code/3b_validate_derived_sites.R` that was never actually created) compares a derived site's reconstructed Hyp/satellite values against the real `Hypernets_matchups` file for the same matchup timestamp, writing `meta/validate_<site>.csv` and printing a per-sensor summary. Purely diagnostic — never blocks the pipeline. See Bugs 12/13 for what it has found so far.
- **Statistics**: `base_stats(x_vec, y_vec)` is the central stats function — computes RMSE, MAPE, MSA, ordinary and log-log linear slope, Model II (SMA) regression with 95% CI via `lmodel2`, and Pahlevan-style median relative Bias/Error in log space (25th/50th/75th percentiles). Returns an all-`NA` row when fewer than 2 valid (positive, non-NA) paired observations exist, or skips Model II specifically (leaving those fields `NA`) when either vector has zero variance (flat NIR bands) **or fewer than 3 valid points remain** (added 2026-09-07 — a 2-point fit has zero residual degrees of freedom, which crashes `lmodel2`'s internal permutation test rather than degrading gracefully; first actually triggered by the `*_raw` sites' unfiltered data). Called symmetrically in both directions (X→Y and Y→X) by `process_global_wavelength()`. Note: `base_stats()` only removes ≤ 0 values; HYPERNETS observations with RHOW > 1 (physically impossible, Bug 3) are not removed here — see the `Hyp > 1` gotcha below.
- **Match-up processing**: `process_matchup_file()` computes pairwise stats between all sensor combinations within one match-up file; `global_stats(site_name, sensor_Y)` aggregates across all files per wavelength, applying the outlier list from `meta/satellite_outliers.csv`, the pre-defined `W_nm_out()` waveband set, and always `daily_closest_matchup()`; `process_sensor(sensor_Z, stat_choice = "matchup")` is the top-level driver, writing both matchup-level and global-level CSVs. There is no `daily_average` parameter any more (removed 2026-09-07) — `daily_closest_matchup()` day-level selection is unconditional in `global_stats()`, since there is no averaging alternative left to toggle (`daily_average_matchups()` was replaced outright back on 2026-09-03). The internal `global_stats_impl(site_name, sensor_Y, select_daily = TRUE)` still exposes a `select_daily = FALSE` escape hatch, used only by `code/3_sensitivity.R`'s before/after comparison to see the un-selected state. Because `global_stats()` builds its file list from `output/matchup_stats_RHOW_<sensor_Z>.csv` (written by the matchup-mode QC gate below) before ever calling `daily_closest_matchup()`, day-level selection only ever runs on matchups that already passed the site's `diff_time`/`dist_limit` QC gate — nothing failing that gate reaches this step. **Time/distance QC gate:** distance uses a flat `dist_limit = 5` km ceiling for every site (a per-sensor `2-3 × sensor_resolution_km(sensor_Y)` version was tried on 2026-09-04 but reverted the same day — it eliminated essentially all MAFR matchups; needs revisiting, not just a 2x/3x guess). Time uses **`site_diff_time_limit(site_name)`** — MAFR = 30 min, THFR = 30 min (both sites, since 2026-09-10) — see `manuscript/roadmap.md`'s "site-specific matchup criteria" item for the empirical comparison (`code/3_sensitivity.R`) and literature review behind raising MAFR from its earlier 15 min (which mirrored Doxaran et al. 2024's tighter Gironde value) to match THFR's 30 min (Doxaran et al. 2024's Berre value).
- **Plotting**: `plot_matchup_*()` family for per-file diagnostics, `plot_global_nm()`/`global_scatterplot()` for the final 1:1 scatter figures with Model II regression lines and CI bands, `global_scatterplot_stack()` for multi-panel composites, `global_scatterplot_waveband()` for per-waveband scatterplots faceted with site as point shape/colour, `plot_matrix_error()` for Figure 11's error/bias matrix heatmap (uses `tidyr::complete()` so a site/sensor combination with zero surviving matchups, e.g. THFR/JPSS2 — Bug 10 — still renders as a labelled grey `NA` cell rather than silently disappearing from the axis).

## Known repo-specific gotchas

- `.gitignore` intentionally lists exception rules after their governing globs — don't reorder without checking pattern precedence.
- **`meta/*_pixel_removals.csv` and `meta/validate_*.csv` are gitignored (added 2026-09-08), not stored in the repo.** They are per-pixel/per-matchup QC and validation audit logs written by `db_export_matchups_*()`/`validate_derived_site()` (see the derived-sites section above), and got large fast — three of the six `*_pixel_removals.csv` files were already 44-52 MB after a single pipeline run, close to or over GitHub's 50 MB soft limit. They were briefly pushed to GitHub, then retroactively removed by amending the commit that introduced them and force-pushing (safe here since that was the same session's own just-pushed tip commit, not deep shared history). Anyone who needs them can regenerate them locally by re-running `code/1_matchups_single.R` (writes the `*_pixel_removals.csv` files) and `code/3_sensitivity.R` (writes the `validate_*.csv` files) against the local `.db` files — they are not required by any other part of the pipeline.
- `figures/` contains the per-family global scatterplot stacks (MODIS/VIIRS/OLCI/OCI), the per-waveband scatterplot stacks, plus Figures 1, 3, 4, 11, and S1 produced by `code/5_figures.R` (see the pipeline-order entry above for what each contains).
- **`5_figures.R` has an `if (!interactive()) quit()` guard** (mirroring the identical guard in `4_matchups_global.R`) right after the global scatterplot/waveband sections. A plain `Rscript code/5_figures.R` run therefore regenerates only those scatterplot stacks, **not** Figures 1/3/4/11/S1 — those require genuinely interactive execution (R console, RStudio, Positron) or shadowing `interactive <- function() TRUE` in the calling session before sourcing the file.
- The outlier CV gate is **not uniform across sensors**: OLCI/MODIS/VIIRS use `cv_limit_choice = 30` (top of `code/2_outliers.R`); OCI uses a hard-coded 50% threshold as a temporary workaround for Bug 8 (`manuscript/upstream-data-bugs.md`) — all THFR PACE files currently exceed 30%, likely because the pixel is extracted several km from the station (Bug 7). Both thresholds are placeholders pending re-extraction of the THFR PACE data. Even the standard 30% gate can legitimately remove 100% of a site/sensor combination (THFR/JPSS2 — Bug 10), which is a real QC outcome, not a bug in the gate itself.
- `daily_closest_matchup()` (added 2026-09-03, replacing `daily_average_matchups()`) picks the single closest-in-time matchup per calendar day rather than averaging same-day matchups together. After this selection, the `file_name` column is dropped (multiple candidate files collapse to one day-record); as a result the `n_clean`/`n_no_out` columns in the global stats CSVs count *files* that passed QC, while the `n` column from `base_stats()` counts *days* — these will differ when multiple same-day matchups exist. Keep that distinction in mind when interpreting matchup counts in the manuscript.
- **`Hyp > 1` filter gap:** the `Hyp <= 1` filter (Bug 3 workaround) is applied inside `global_scatterplot()` before plotting, but **not** inside `global_stats()` before computing statistics. `base_stats()` removes ≤ 0 values but not > 1 values. If any MAFR matchups contain HYPERNETS RHOW > 1 at any waveband, those observations will influence the statistics CSVs but not the figures — check and add the filter inside `global_stats()` if needed (see roadmap open item 11).
- **A row present but `NA` differs from a row absent.** A waveband can show `NA` in Figure 11/the stats CSVs for two distinct reasons: (1) the row exists but `base_stats()` returned an all-`NA` row because fewer than 2 (or, for Model II specifically, fewer than 3) valid positive paired observations remained at that waveband, or (2) the site/sensor combination has zero surviving matchups at all (e.g. THFR/JPSS2 — Bug 10), which `plot_matrix_error()`'s `tidyr::complete()` now backfills into a labelled grey cell for every sensor family.
- **The satellite pixel-box reconstruction does not closely match the real tool, and this is expected, not a bug to chase (Bug 13).** `write_matchup_csv_db()`'s plain arithmetic mean of surviving pixels differs from `Hypernets_matchups`' own satellite value by a persistent 3-58% median across every derived site tested (`THFR_NE`/`THFR_poly`/`THFR_pixel`/`MAFR_pixel`, and now `THFR_raw`/`MAFR_raw` too) — the real tool's weighting/exclusion formula is undocumented and not recoverable from the `.db` schema. The Hyp side, by contrast, is essentially exact (~0.00001-0.5% median) since Bug 12's fix. Don't treat a large `Sat_pct_diff` in `meta/validate_*.csv` as a sign something in this repo is broken unless it's meaningfully outside that existing range.
- **`meta/<site>_pixel_removals.csv` and `output/matchup_stats_RHOW_*.csv` don't share a join key yet.** The removal log is keyed by `matchup_id` (plus `db_source`/`dateTime_Hyp`/`dateTime_sat`, which `db_matchup_filename()` can turn into the same `file_name` the stats CSV uses); the stats CSV has no `matchup_id` column at all for any site today. A "which pixels were screened" summary on the good-matchup side is designed but not yet wired in — see the TODO in `code/2_outliers.R`.
